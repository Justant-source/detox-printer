# M832 프로토콜 (C단계 — 벤더 필터 오프라인 실행 결과)

> **중요: WIDTH_BYTES는 하드웨어 고정값이 아니라 PPD `PageSize` 선택에 종속된다.**
> M832.ppd는 A4/Letter/w110h146(110mm×146mm)/w80h106/w53h70 5종의 PageSize를 지원한다.
> 아래 "전체 구조" 절은 최초 A4로 테스트한 결과이며, **사용자가 실제 장착한 용지는 110mm 폭**이므로
> `## 110mm(w110h146) 용지 실측` 절의 값(WIDTH_BYTES=163)이 이번 인쇄에 적용되는 확정값이다.

> 출처: `rastertoM08F`(x86_64) 오프라인 실행, `DEVICE_URI=bluetooth://offline`,
> 입력은 `cupsfilter -p ppds/M832.ppd`로 변환한 A4(2480x3508px@300dpi) PNG 4종.
> 소스 분석은 `docs/filter-source-map.md` 참고. 아래는 전부 [확인됨] — 실제 필터 출력 바이트 기준.

## 전체 구조 (t1/t2/t3/t4 공통, 1,003,410 bytes)

| 오프셋 | 길이 | 내용 | 의미 |
|---|---|---|---|
| 0 | 3 | `1f 11 0b` | 미디어 타입: 연속용지(zeMediaTracking=Continuous) |
| 3 | 4 | `1f 11 35 00` | 압축 Off |
| 7 | 8 | `1d 76 30 00 20 01 9c 0d` | bCmdBMP: `1D 76 30 00` + xL xH yL yH |
| 15 | 1,003,392 | 래스터 비트맵 | WIDTH_BYTES×HEIGHT_LINES, MSB-first, **1=검정** |
| 1,003,407 | 3 | `1f 11 11` | findpaper — 작업 종료 시 질의(831 외 전 모델 공통, 응답 대기는 오프라인 실행에선 무시됨) |

**주의**: `bCmdDensity(1F 11 02 xx)`·`bCmdSpecial(1F 11 37 xx)`가 헤더에 없음 — PPD Darkness 옵션이 `Default`(명시적 마킹 없음)일 때 StartPage가 이 명령을 생략하는 것으로 보임 [미검증·소스미확인, cupsfilter에 `-o Darkness=...` 옵션을 명시하면 재확인 필요].

## bCmdBMP 필드 해석

```
1d 76 30 00 20 01 9c 0d
            ^^ ^^ ^^ ^^
            xL xH yL yH
```
- xL=0x20=32, xH=0x01=1 → **WIDTH_BYTES = 32 + 1×256 = 288**
- yL=0x9c=156, yH=0x0d=13 → **HEIGHT_LINES = 156 + 13×256 = 3484**
- 검증: 288 × 3484 = 1,003,392 = 실제 비트맵 길이. 15(헤더) + 1,003,392 + 3(푸터) = 1,003,410 = 파일 전체 크기. 정확히 일치

## A단계 PPD 계산값과의 교차 검증 — 불일치, 원인 확인됨

| | 값 | 근거 |
|---|---|---|
| A단계 PPD 계산 (잠정) | 296 byte (2361 dot) | ImageableArea 전체 폭 `14.17~580.83`pt 기준 |
| **C단계 실측 (확정)** | **288 byte (2304 dot)** | bCmdBMP xL/xH |

원인: `cupsfilter`의 `imagetoraster`가 이미지를 "auto orientation + fit" 방식으로 배치하면서 실제 사용한 `ImagingBoundingBox`가 `[21 29 574 811]`pt(폭 553pt→2303dot, PPD의 `14.17~580.83`=566.66pt→2361dot과 다름)였고, 이를 8의 배수로 올림(`nw`)해 2304dot=288byte가 됨. **PPD의 ImageableArea는 "최대 가능 폭"이고, 실제 인쇄 폭은 cupsfilter의 이미지 배치 로직(스케일링·중앙정렬)에 따라 더 좁아질 수 있다** — E단계에서 pyusb로 직접 이미지를 패킹할 때는 cupsfilter를 거치지 않으므로, 최종 WIDTH_BYTES는 "몇 dot을 프린터에 실제로 보낼 것인가"를 우리가 직접 정의하기 나름이다(288은 이번 특정 변환 경로의 산출값이지 하드웨어 한계값이 아님). 하드웨어가 실제로 몇 dot까지 인쇄 가능한지는 D단계(CUPS 실물 인쇄) 또는 F-2(헤드 폭 실측)에서 확정한다.

## 높이 패딩 (HEIGHT_LINES 3484)

- cupsfilter가 보고한 `cupsHeight`=3257, 필터 내부에서 `nw`(폭)=2304로 8배수 정렬 후 `width: 2304, height: 3257`으로 처리
- 최종 bCmdBMP의 yL/yH는 3484 — `docs/filter-source-map.md`의 M832 연속용지 높이 패딩 로직(A4=295mm×300dpi/25.4=3484.25→3484) 그대로 확인됨. 즉 3257줄의 실제 이미지 데이터에 3484-3257=227줄만큼 패딩이 뒤에 붙는다
- **패딩의 패킹된 바이트값은 0x00**(E-2, `src/06_generate.py`로 t3.bin과 바이트 단위 실측 확인). 소스의 `memset(tempbuf, 0xFF, ...)`(흰색=255, `docs/filter-source-map.md` (e))는 패킹 **이전**의 1byte/pixel 그레이스케일 버퍼 기준값이고, 이후 `OutputLine`의 `pixelColor <= 128` 임계값을 통과하면서 255(흰색) → 비트 0으로 패킹된다. 즉 그레이스케일 0xFF(흰색)가 패킹되면 바이트 0x00(1=검정 극성 기준 흰색)이 되는 게 맞다 — "0xFF 패딩"이라는 표현은 그레이스케일 단계에서만 유효하며 최종 바이트 값과 혼동하면 안 된다

## 압축 여부 — Off 확인됨

- 헤더에 명시적 `1f 11 35 00`(압축 Off) 마커
- t1(전면 흰색)과 t2(전면 검정)의 파일 크기가 완전히 동일(1,003,410 byte) → 내용에 따라 크기가 변하지 않음 = 비압축 raw 비트맵 확정

## 비트 극성 — 1=검정 확인됨

- t1(전면 흰색) vs t3(좌상단 100×100 검정 사각형) 비교: 첫 차이가 오프셋 15(비트맵 시작 직후)에서 발생, `t1[15]=0x00`, `t3[15]=0xff`
- 흰 배경은 전부 0x00, 검정 영역은 0xff → **1비트=검정**, 반전(`~`) 없음. `docs/filter-source-map.md`의 OutputLine `case M832` 분석과 일치

## 결정성 — 1건의 비결정적 타임아웃 발견 (재현 안 됨)

- t1/t2/t4는 각각 첫 실행에서 `timeout 30` 내 정상 종료(exit 0)
- **t3만 최초 실행에서 `exit 124`(30초 타임아웃)로 잘림(999,424 byte)**. 재시도 시 1.2초 만에 정상 종료(exit 0, 1,003,410 byte, stderr 로그 tail 완전 동일)
- 원인 미상 — 4개 필터 프로세스를 연속으로 빠르게 실행한 것과 관련된 일시적 자원 경합으로 추정되나 [미검증]. 재현되지 않아 추가 조사 보류. 이후 단계(특히 E-1 실제 USB 응답 대기)에서 유사한 비결정적 지연이 나타날 수 있음을 유념

## 통과 조건 확인 (A4 기준)

- [x] 헤더/데이터/푸터 경계를 바이트 오프셋으로 특정 (0-6 / 7-14 / 15-1003406 / 1003407-1003409)
- [x] 압축 여부 판정 (Off, raw)
- [x] 라인당 바이트 수를 A단계 계산과 대조 → **불일치 확인 및 원인 규명** (288 vs 296, cupsfilter 이미지 배치 로직 차이)

## 110mm(w110h146) 용지 실측 — 사용자 실제 장착 용지 [확인됨]

> M832.ppd의 `w110h146`(110mm×146mm) PageSize 사용. `-o PageSize=w110h146`로 cupsfilter 재실행.
> **주의(방법론 기록)**: A4용으로 만든 2480×3508 소스 PNG를 그대로 이 PageSize에 통과시켰더니
> cupsfilter가 종횡비를 맞추며 리스케일하는 과정에서 좌상단 100×100 사각형이 통째로 잘려나가
> t1(백색)·t3(모서리)·t4(가로선) `.ras`가 완전히 동일해지는 문제가 있었다(md5 동일 확인).
> **매체 크기를 바꿔 테스트할 때는 반드시 그 매체의 실제 cupsWidth/cupsHeight에 맞춘 소스 이미지를
> 새로 만들어야 한다** — 다른 매체용 이미지를 그대로 재사용하면 소리 없이 잘못된 결과가 나올 수 있다.
> 아래는 1300×1724px(해당 매체의 실제 cupsWidth/cupsHeight)로 새로 만든 이미지 기준.

| 항목 | 값 |
|---|---|
| ImageableArea | `0 0 312 414` pt (풀블리드, 여백 없음 — A4/Letter와 달리 마진 없음) |
| cupsWidth / cupsHeight | 1299~1300 / 1724~1725 (반올림 오차 ±1) |
| **WIDTH_BYTES (bCmdBMP xL/xH)** | **163 byte (1304 dot)** |
| HEIGHT_LINES (내용에 따라 가변) | 실제 이미지 높이 그대로 (A4/Letter 같은 고정 패딩 없음 — `cupsPageSizeName`이 "A4"/"Letter"가 아니면 `else { tmph = header.cupsHeight; }`, filter-source-map.md (e) 참고) |
| 압축 | Off (A4와 동일) |
| 비트 극성 | 1=검정 (A4와 동일, t1 vs t3 재확인: 오프셋15에서 `0x00`→`0xff`) |
| 헤더 | `1f 11 0b` `1f 11 35 00` `1d 76 30 00 <xL><xH><yL><yH>` (A4와 동일 구조) |
| **푸터 (A4와 다름!)** | `1b 64 01` (페이지별, M832After) + `1b 64 02` (작업 종료) + `1f 11 11`(findpaper) — **PageSize가 A4/Letter가 아니므로 bCmdAfter가 실제로 발동함**(filter-source-map.md (c) 예측과 정확히 일치) |

**결정성**: 이번에도 최초 실행에서 t2/t3가 30초 타임아웃(exit 124)됐다가 재시도 시 즉시 성공 — A4 테스트의 t3 사례와 같은 패턴의 1회성 비결정적 지연. 두 번 모두 재현 불가. E-1 실제 USB 전송 시 유사한 지연에 대비해 넉넉한 타임아웃과 재시도 로직을 유지할 것.

**결론**: 사용자가 실제로 장착한 110mm 용지에 대해서는 **WIDTH_BYTES=163byte**를 사용해야 한다. A4용으로 만들어둔 `src/06_generate.py`·`src/07_print_image.py`의 `WIDTH_BYTES=288`은 이 용지에 맞지 않으므로, 실제 인쇄 전에 폭 파라미터를 163으로 바꾸거나 `--width-bytes` 옵션으로 넘겨야 한다.
